# Test128：修正测试对端的 ACK 条件

本轮只更新采集工具，继续使用 Test127 驱动和原单包程序，不重写 EFI。

Test127 的受控 awdl0 回包已成功，但发送完成通知仍缺失。旧 OpenWrt 工具只建立普通 monitor，没有核对运行中的接口 MAC，也没有配置 active monitor。应用层回复不能证明原请求收到 Wi-Fi 硬件 ACK。

Test128 在关闭临时使用的 AP 前，先只读查询当前 PHY 的真实能力；随后显式创建 active monitor，并在启动对端前重读接口身份、MAC 和频道。任一条件不满足就停止，不降级到旧模式。WAN/LAN、另一频段和原有恢复流程保持原约束。

本机能力查询和本轮运行均已确认 active monitor 配置生效，接口 MAC 与请求接收地址一致。它不等于独立抓到了 ACK，更不等于 AirDrop 成功。

`coordinate_peer_test128.py` 默认只校验并输出计划，只有显式 `--run` 才会进入原有 Test127 实机预检。运行前须按新启动生成私有配置，并将监控脚本、原 echo 程序和能力查询程序暂存至本轮独立目录。`prepare_peer_mac_required` 必须为 `true`，能力程序受源码与二进制哈希绑定。

## 本轮结果（2026-11-09）

仍加载 `25G416-Test127`，使用 Test128 对端工具；没有修改驱动、帧或 350 ms 等待预算。

| 检查 | 结果 |
| --- | --- |
| 对端配置 | active monitor 与实时 MAC 核对通过 |
| 发送完成 | 对应队列、描述符、帧头和长度的 TX_RSP 到达；门铃后 49.364 ms，状态 `0x01`，固件报告发送成功 |
| 原生回包 | 8 字节 UDP 的同标记回包在 52.256 ms 到达 awdl0 socket |
| 独立 ACK 抓取 | 未覆盖；不把固件成功或应用回包改写成直接观测到 ACK |
| 完整安全释放 | 未通过，`EBUSY`；外层清理仍被阻断 |
| 路由器恢复 | 首次恢复命令失败，watchdog 恢复后幂等复验通过；配置哈希不变，临时目录已归档清理 |

相比前一轮没有 TX/BA 完成记录，本轮首次取得同包的精确发送完成。改变对端条件后结果有改善，但一次对照不能证明所有设备和频道都适用。

收尾记录显示 HAL 已关闭、队列和站点已退役，binding 与 PHY 租约也已释放，但外层 P2P MAC 仍存在。源码有明确的终态衔接矛盾：ROC 清理成功后置为 `COMPLETE`，后续内部资源检查却只接受 `IDLE`。这与本轮失败路径吻合；最终 ROC phase 没有在该快照直接发布，因此区分源码推断与实测字段。

下一版应只修正成功清理路径的同代终态证明，保留通用 DMA 和未知状态保护；还要验收外层 MAC 删除回执，不能仅凭内部 `Stage8` 宣布全部释放。本轮不再发包，不重写 EFI；联网冒烟、睡眠与 AirDrop 文件传输均未执行。
